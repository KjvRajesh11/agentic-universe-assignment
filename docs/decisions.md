# Architecture Decision Records (ADRs) & Assumptions

| Decision ID | Decision Title | Context & Specification Gap | Chosen Approach & Rationale | Alternatives Considered |
| :--- | :--- | :--- | :--- | :--- |
| **ADR-001** | **HMAC-SHA256 vs Blind Indexing for Phone Identity** | How to index and look up leads by phone without storing plaintext PII. | Keyed HMAC-SHA256 fingerprint on canonical `+91XXXXXXXXXX`. Prevents rainbow-table enumeration while allowing $O(1)$ relational lookups. | Unkeyed SHA-256 (insecure against dictionary search), full-table decryption (catastrophic $O(N)$ performance). |
| **ADR-002** | **Append-Only Interaction Ledger for Disposition Overrides** | Specification requires that disposition overrides never edit or delete previous historical events. | All events are strictly appended to `interaction_ledger`. Effective disposition is resolved dynamically via SQL/query aggregation based on latest `occurred_at_epoch`. | In-place update of original `disposition.set` (destroys audit trail, violates compliance rules). |
| **ADR-003** | **Orphan Event Handling & Multi-Pass Reconciliation** | Events can arrive before their lead in earlier drops. | Quarantined events stored in `quarantined_events`. When new drops arrive, a reconciliation loop runs until fixed-point convergence to link newly available leads and resolve subsequent overrides. | Dropping unlinked events permanently (data loss), holding open uncommitted transactions across drops (high memory/deadlock risk). |
| **ADR-004** | **Rejection Priority in Schema Order** | A CSV row may fail multiple criteria simultaneously (e.g. missing name and invalid phone). | The row is evaluated against schema fields in exact schema order. The first rule failure immediately terminates evaluation and assigns the single reason. | Multi-reason composite errors (violates output contract of `rejections.csv`). |
| **ADR-005** | **Field Warnings Accounting Boundary** | Should field warnings on optional fields be counted for rows that are subsequently rejected? | Spec rule: "Count warnings only for rows that are not rejected." Warnings are collected during parsing but only committed to the quality counter if the row passes validation. | Counting warnings on rejected rows (inflates field warnings metric). |
| **ADR-006** | **Permanent Batch ID Preservation** | When a duplicate lead arrives in `batch_002` after being introduced in `batch_001`, which batch ID applies? | The original `batch_id` (`batch_001`) remains permanent. The later row merges non-null attributes only. | Overwriting `batch_id` on merge (corrupts client cohort reporting). |
| **ADR-007** | **Atomic File Generation for Reports** | Clients and downstream jobs consume generated CSVs and JSON reports. | Reports are written to temporary files in the target directory and atomically moved into place using `os.replace`. | Direct in-place file writes (leaves corrupted partial files if interrupted). |
| **ADR-008** | **SQLite with In-Memory Caching for High Scale** | Ingesting 140,000 leads and 632,000 events must run in under 2 minutes. | SQLite in WAL mode with normal synchronous writes, combined with an in-memory `(workflow_id, phone_fp) -> lead_id` cache and single-pass stream processing. | PostgreSQL (heavier infrastructure overhead for take-home assessment), pure in-memory SQLite (no durability). |
